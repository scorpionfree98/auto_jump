# 实时点击落点设计

## 问题

小米 14 Pro 的飞书考勤小程序同时暴露两个文本为“打卡”的节点。录制坐标可用于区分中间按钮和底部导航，但中间按钮会随页面布局发生位移。本次失败中，录制纵坐标为 `0.545`，当前页面中间“打卡”文字中心为约 `0.472`。系统接受旧坐标手势并不代表目标按钮实际收到点击，因此日志出现了伪成功。

## 方案比较

1. **用录制坐标选择候选，再点击候选的实时中心（采用）**：录制坐标只负责在同名节点中选出最近者；若该节点只能找到覆盖大半屏幕的可点击父容器，则在当前节点中心派发坐标手势。页面没有匹配节点时才使用录制坐标兜底。兼顾同名控件区分和页面位移。
2. **把现有规则坐标手工改到按钮中心**：改动小，但页面再次位移后仍会失败，也无法泛化到其他应用。
3. **点击后识别业务成功状态并重试**：可靠性更高，但需要配置每个目标页面的成功文案，超出当前通用规则模型范围，且存在重复触发业务动作的风险。

## 数据流

`AccessibilityNodeFinder` 为每个候选保存当前屏幕上的归一化中心。`ClickTargetResolver` 先按控件 ID、文字、描述的优先级匹配，再用录制坐标选择最近的同名候选。精确可点击节点继续执行无障碍节点点击；可点击父容器过大的画布节点返回带候选信息的手势决策。服务使用候选实时中心派发手势；只有没有候选的超时回退才使用规则中的录制坐标。

## 安全与验证

- 不自动重试已被系统接受的业务点击，避免重复打卡。
- 无有效录制坐标时不对不精确画布候选派发手势。
- 单元测试覆盖：同名候选择近、不精确候选使用实时中心、无候选仍使用录制坐标回退。
- 在 120 Docker 环境执行 JVM 测试、Android Lint 和 Debug APK 构建。
- 小米 14 Pro 只验证 deeplink、候选位置和决策落点；实际考勤点击由用户主动确认后执行。
