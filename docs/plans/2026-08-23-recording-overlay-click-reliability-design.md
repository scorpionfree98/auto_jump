# 录制悬浮窗点击可靠性设计

## 问题与根因

点击动作编辑器打开 deeplink 后，无障碍服务会在目标应用顶部显示“开始录制 / 取消”悬浮窗。当前服务把收到的每一个窗口内容变化和点击事件都当成前台应用变化；悬浮窗自身、输入法、系统提示或目标应用的瞬时辅助事件都可能短暂携带不同包名。按钮按下到抬起之间一旦发生这种事件，服务就会误判用户已经离开目标应用并移除悬浮窗，表现为按钮可见但偶发点不上。

另一个放大因素是按钮回调直接读取控制器中可变的请求 ID 和目标包名。窗口在同一触摸周期内被刷新时，这些字段可能先被清空，导致合法点击不能启动录制。

## 方案选择

不把悬浮窗改成可聚焦或全屏触摸层，因为这会遮挡目标应用；也不改成通知栏操作，因为会增加录制步骤并破坏现有流程。采用活动窗口校验：优先读取 `getRootInActiveWindow()` 的包名，只在可信的窗口状态变化时才使用事件包名；忽略 AutoJump 悬浮窗自身和普通内容变化带来的瞬时包名。真正切换应用时，活动窗口仍会更新，因此悬浮窗可以正常隐藏。

悬浮窗创建时为点击监听器保存不可变的请求 ID 和目标包名，并在第一次点击后立即禁用两个按钮，避免快速连点或窗口更新重复触发。按钮保持非模态、不抢焦点，主操作触摸高度提升到至少 56dp。

## 验证

增加纯 Java 前台窗口跟踪单元测试，覆盖目标应用、AutoJump 自身事件、普通内容事件、系统窗口和真实切换。现有录制策略、延迟计算和敏感界面拒绝测试继续运行。

120 Android 9 模拟器开启 AutoJump 无障碍服务，进入外部目标应用后显示录制悬浮窗。连续多轮执行“显示悬浮窗 → 注入内容变化 → 点击开始录制”，每轮都必须转为 `ARMED`、悬浮窗消失且无崩溃；同时截图确认按钮尺寸和位置。最终执行全部 36+ 单元测试、Android Lint 和 Debug APK 构建，并校验固定调试签名不变。
